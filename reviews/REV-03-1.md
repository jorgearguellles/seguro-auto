# REV-03-1 — Resumen de cotización y pago simulado (US-03)

## Resumen

critical: 2 · major: 5 · minor: 6 · nit: 3

El paso 3 está bien cableado en general: `TermsBlocksRenderer` cumple ADR-009 §D3-A al dedo (cero `innerHTML`, cero `bypassSecurityTrustHtml`, interpolación Angular pura, validación de enlaces vía `isSafeUrl`), `parseTerms` replica el patrón tolerante de ADR-006 (envelope → documento → body con `discriminatedUnion` + descarte + log), `PaymentService` cumple AC-03.5/6/7 con `shareReplay(1)` para idempotencia y timer determinista, `generateQuoteNumber` usa `crypto.getRandomValues` con fuente inyectable (ADR-010 §D2-B exacto). La cobertura de tests es buena (226 tests pasan, incluyendo 9 de `maskDocument`, 15 de `PaymentService` y 12 de `parseTerms`), el e2e cubre los 17 ACs de la spec, y la seguridad de red se mantiene: cero tokens en `apps/web`, cero `populate=*`, cero `any`.

Sin embargo hay **dos bugs críticos de integración CMS↔front** que rompen requisitos privacy-crítico en runtime real:

1. **`maskDocument` nunca se dispara contra el seed real.** El seed de Strapi usa `documentNumber_CO`, `documentNumber_CL`, `rut_CL` como `key`, pero `SummaryComponent.applicantEntries` compara literalmente contra `'documentNumber'`, `'rut'`, `'cedula'`. En consecuencia, al conectar contra Strapi de verdad (Docker), el número de documento **completo** se renderiza en el DOM del paso 3 — violando RN-03.11, AC-03.16 y la regla de privacidad de CLAUDE.md §7. Los e2e pasan porque el fixture `CO_FIELDS_RESPONSE` usa `key: 'documentNumber'` sin sufijo. Mismo patrón del bug F-01-1.1.
2. **Divergencia `/api/legal-terms` vs ADR-009.** El `schema.json` define `pluralName: "legal-terms"` y el front llama a `/api/legal-terms`. ADR-009 §Esquema concreto y §Consecuencias fijan expresamente `pluralName: 'terms'` con test de integración `GET /api/terms` esperando 200. Un ADR aceptado es inmutable (CLAUDE.md §6.2) y esta decisión requería un supersede/delta formal. El commit `a7c1fd2` menciona "conflict" sin ADR que lo respalde.

Hay además una **violación de RN-03.1**: la spec exige tres bloques (titular, vehículo, plan) y la implementación renderiza sólo dos (datos combinados + plan). El e2e lo tapa porque cuenta "Términos y condiciones" como tercer bloque, lo cual no es lo que dice el AC-03.1.

Divergencias de ADR adicionales dignas de anotar: la ruta de confirmación spec'd como `/:country/confirmacion` con `confirmacionGuard` (ADR-010 §D3-A, §D4-A) se sustituyó por un estado interno `pageState='confirmed'` dentro del mismo componente + `router.navigate([mismo url], {replaceUrl:true})`. El efecto neto puede parecerse pero `replaceUrl` sobre la misma URL es un no-op para Angular (comportamiento por defecto `onSameUrlNavigation:'ignore'`) y no hay guard sobre `quoteNumber`. La ubicación del renderer tampoco es la que ADR-009 §D3-A mandó (`features/wizard/terms/`); vive en `features/summary/`.

Comandos ejecutados:
- `npm --prefix apps/web test` → **226 passed**.
- `npm --prefix apps/web run lint` → no completó por timeout del sandbox, pero sin output de error visible.
- `grep` para tokens, `populate=*`, `innerHTML`, `: any` → sin resultados en `apps/web/src`.

## Hallazgos

### F-03-1.1 · critical · Seguridad / privacidad (RN-03.11, AC-03.16, CLAUDE.md §7)

**Dónde:**
- `apps/web/src/app/features/summary/summary.component.ts:529-533` (keys hard-coded)
- `apps/cms/src/seed.ts:137, 156, 206, 272` (keys reales `documentNumber_CO`, `documentNumber_CL`, `rut_CL`)
- `apps/web/e2e/fixtures/form-fields.ts:24` (fixture usa `key: 'documentNumber'` sin sufijo)

**Evidencia:**
```ts
// summary.component.ts
return Object.entries(applicant).map(([key, value]) => {
  const stringValue = value === null || value === undefined ? '' : String(value);
  const maskedValue =
    key === 'documentNumber' || key === 'rut' || key === 'cedula'
      ? maskDocument(stringValue)
      : stringValue;
  return { key, value: maskedValue };
});
```
```ts
// seed.ts
{ key: 'documentNumber_CO', ... }
{ key: 'documentNumber_CL', ... }
{ key: 'rut_CL',             ... }
```

Las keys del seed llevan sufijo `_CO` / `_CL`; las comparaciones en `applicantEntries` son literales exactas sin sufijo. Contra Strapi real, `maskDocument` **nunca** se invoca → el DOM contiene el documento completo del usuario.

El fixture del e2e (`form-fields.ts`) usa `key: 'documentNumber'` plano, por lo que los tests de AC-03.2 / AC-03.16 pasan verde con cobertura falsa.

**Por qué importa:** rompe la regla de privacidad más alta del paso 3. RN-03.11 ("el número de documento completo no debe estar presente en el DOM del resumen") y AC-03.16 ("la cadena `1023456789` no aparece en ningún nodo de texto, atributo `title`, `aria-label` ni `data-*`") son explícitos. CLAUDE.md §7 reitera el requisito. Es el mismo patrón que F-01-1.1: dos contratos (CMS vs. front) que no comparten enum/convención de keys.

**Recomendación:**
- Opción A (quirúrgica, respeta el seed): reconocer las keys por **prefijo/regex**. Reemplazar la comparación por una función `isDocumentKey(key: string)` que acepte `documentNumber*`, `rut*`, `cedula*` (case-insensitive). Añadir test unitario con las tres keys del seed real.
- Opción B (mejor a largo plazo): marcar los campos sensibles en Strapi con un atributo (p.ej. `sensitive: boolean` o `section: 'applicant-id'`) y leer esa bandera. Documentar en un ADR delta a ADR-001.
- Opción C (más conservadora): normalizar keys en seed y fixture a un único nombre canónico `documentNumber` + `rut` (sin sufijo) — pero romper el seed existente requiere cuidado con el resto del wizard.
- Alinear el fixture de e2e con las keys reales del seed (`documentNumber_CO` etc.) **después** de arreglar la lógica, para que AC-03.16 proteja de verdad contra regresiones.
- Añadir un test de integración (o e2e) que levante Docker + Strapi real + Playwright y haga `expect(page.content()).not.toContain('<documentoreal>')`. Hoy el test lo hace pero contra el fixture, no contra el seed.

**Estado:** open

### F-03-1.3 · major · Cumplimiento de spec (RN-03.1, AC-03.1)

**Dónde:** `apps/web/src/app/features/summary/summary.component.ts:114-150`

**Evidencia:** la plantilla renderiza **dos bloques** bajo el estado `@default`:
1. `Block 1: Applicant data` — todas las entries del `applicant` juntas (titular + vehículo).
2. `Block 2: Plan summary`.

Los datos de vehículo (`plate_CO`, `vehicleYear`, `brand_CO`) se muestran dentro del mismo bloque `"Tus datos"` que el titular.

Spec SPEC-03 §3 RN-03.1: *"El resumen muestra tres bloques: datos del titular (paso 1), datos del vehículo (paso 1) y plan elegido (paso 2) con su precio final."*

AC-03.1:
> *"Then veo un bloque con los datos del titular que ingresé*
> *And veo un bloque con los datos del vehículo que ingresé*
> *And veo un bloque con el plan elegido ..."*

E2e `AC-03.1 paso-3 shows three sections: datos, plan and términos` (`paso-3.spec.ts:248-263`) cuenta "Términos y condiciones" como el tercer bloque — lo cual coincidentalmente deja al test en verde pero **no es** lo que el AC pide. El AC-03.1 no menciona el bloque de términos como parte de los "tres bloques" del resumen (el bloque de términos vive en una sección aparte, AC-03.3).

**Por qué importa:** es un AC de la spec no cumplido literalmente. Afecta UX (todo mezclado en un `dl` largo es menos escaneable) y confunde la trazabilidad (el test dice que cubre AC-03.1 pero no verifica la condición concreta de "tres bloques: titular, vehículo, plan").

**Recomendación:**
- Dividir `applicantEntries` en `applicantIdentityEntries` + `vehicleEntries` filtrando por `field.section` (el seed ya marca `section: 'applicant' | 'vehicle'`). Esto requiere persistir también los `fields` del paso 1 en el `WizardStore` o rehacer la consulta — lo más barato es que `WizardStore.applicantFieldsSnapshot` pase a ser `FormField[]` (ya incluye `section`) o que el componente pida los fields a Strapi una vez (misma query del paso 1).
- Renderizar dos `<section>` separados: "Datos del titular" / "Datos del vehículo", cada uno con su encabezado y su enlace "Editar datos".
- Ajustar el e2e AC-03.1 para contar 3 bloques del resumen propiamente dichos y un cuarto bloque de términos.

### F-03-1.4 · major · Cumplimiento de ADR (ADR-010 §D3-A, §D4-A)

**Dónde:**
- `apps/web/src/app/app.routes.ts` (no existe ruta `/:country/confirmacion`)
- `apps/web/src/app/wizard/wizard-step.guard.ts` (no existe `confirmacionGuard`)
- `apps/web/src/app/features/summary/summary.component.ts:596-600`

**Evidencia:**
```ts
if (outcome.ok) {
  this.wizardStore.setQuoteNumber(outcome.quoteNumber);
  // ADR-010 D4-A — replaceUrl prevents back-button to payment
  const country = this.#countryContext.country().toLowerCase();
  this.pageState.set('confirmed');
  void this.#router.navigate([`/${country}/paso-3`], { replaceUrl: true });
}
```

ADR-010 §D3-A mandó:
> *"La pantalla de confirmación debe vivir dentro de la rama `/:country/*` para poder leerlo. ... Nuevo guard de la ruta de confirmación: `confirmacionGuard: CanActivateFn = () => { ... if (store.quoteNumber() == null) return router.createUrlTree(['/', country, 'paso-1']); return true; };`"*

ADR-010 §D4-A mandó:
> *"`router.navigate([..., 'confirmacion'], { replaceUrl: true })`: la entrada del history 'resumen de pago' se reemplaza por 'confirmación'."*

La implementación navega a **la misma URL** (`/co/paso-3`) con `replaceUrl: true`. Esto tiene tres consecuencias:

1. `onSameUrlNavigation` por defecto en Angular Router es `'ignore'` → el `navigate` es un no-op; el router no re-ejecuta guards ni reemplaza la entrada del history. El `replaceUrl` no se aplica. El estado `pageState='confirmed'` se mantiene en memoria del componente.
2. En el e2e `AC-03.17`, `page.goBack()` navega a la entrada previa (paso-2). La "protección" funciona por **coincidencia** porque el guard de paso-3 no se re-dispara en esa navegación y la URL anterior (paso-2) es una pantalla válida.
3. No hay `confirmacionGuard`: si el usuario refresca estando en pantalla de confirmación (F5), el componente se reinicia y `pageState='loading'` → la pantalla de confirmación desaparece, el `quoteNumber` del store se mantiene pero no se muestra. El ADR-010 §D3-A lo esperaba vía `confirmacionGuard`.

**Por qué importa:** ADR-010 §D3-A/D4-A son contratos explícitos y testeables ("Test unitario `confirmacionGuard redirects when quoteNumber is null`"). Ninguno de esos tests existe. La implementación resuelve AC-03.17 por accidente, no por diseño; cualquier futuro cambio (p.ej. activar `onSameUrlNavigation: 'reload'` para refrescar algo) puede romperlo sin avisar.

Además AC-03.14 pide *"la pantalla de confirmación mueve el foco a un encabezado con role=status o aria-live=polite"*. El `<h2 class="confirmed-heading">` tiene `tabindex="-1"` en el contenedor pero **nadie llama a `.focus()`**. El foco se queda en el botón "Pagar" (si no fue destruido) o pierde la ubicación. Afecta a11y de lectores de pantalla.

**Recomendación:**
- Crear `/:country/confirmacion` como route hermana de `paso-3`, con `confirmacionGuard` (chequea `quoteNumber() != null`), componente propio (`SummaryConfirmationComponent`) que lee `store.quoteNumber()` y mueve el foco al `<h2>` en `ngAfterViewInit`.
- `SummaryComponent.onPay()` hace `router.navigate(['/', country, 'confirmacion'], { replaceUrl: true })` — URL **distinta**, `replaceUrl` sí aplica.
- Añadir los tests spec'd en ADR-010 §Validación: `confirmacionGuard redirects when quoteNumber is null`, `AC-03.14 keyboard focus moves to confirmation heading`.
- Si el humano acepta mantener la confirmación dentro del mismo componente, documentarlo en un ADR-010 v2 / supersede.

**Estado:** open

### F-03-1.5 · major · Cumplimiento de ADR (ADR-009 §Esquema concreto, SPEC-03 §6)

**Dónde:** `apps/cms/src/api/terms/content-types/terms/schema.json:12-29`

**Evidencia:**
```json
"attributes": {
  "title": { "type": "string", "required": true },
  "body": { "type": "blocks" },
  "effectiveDate": { "type": "date", "required": true },
  "country": { "type": "relation", ... }
}
```

Dos divergencias con ADR-009 §Esquema concreto:

1. **Falta el campo `version`** (`type: string`, opcional, "etiqueta legible v1.0"). ADR-009 lo lista explícitamente; SPEC-03 §6 lo lista como atributo informativo. Negocio **no puede** poner una etiqueta de versión, y el schema zod ya la consume (`version: z.string().optional().nullable()`), por lo que viene `undefined`.
2. **`body` no está marcado `required: true`.** ADR-009 dice "sí" para `body` (obligatorio). Un operador podría publicar un documento con `body: null` en Strapi; el front hace `.default([])` en zod, por lo que no romperá, pero el contrato CMS no refleja el ADR.
3. **`effectiveDate` es `required: true`** en el schema pero ADR-009 lo pone opcional ("no obligatorio, utiliza `updatedAt` como fallback"). Divergencia menor, pero bloquea al operador que quiera publicar un documento sin fecha.

**Por qué importa:** el contrato de Strapi es parte del ADR aceptado; la implementación lo erosionó sin justificar. El `version` ausente deshabilita la trazabilidad de términos que ADR-009 §Camino de evolución anticipa.

**Recomendación:**
- Añadir `"version": { "type": "string" }` al schema.
- Cambiar `body` a `"required": true` (coincide con el seed real).
- Decidir si `effectiveDate` debe ser requerido o no; si sí, actualizar ADR-009 vía changelog; si no, quitar `required: true`.
- Reflejar los cambios también en el seed si procede.

**Estado:** open

### F-03-1.7 · major · Accesibilidad (AC-03.14)

**Dónde:** `apps/web/src/app/features/summary/summary.component.ts:93-108`

**Evidencia:**
```html
@case ('confirmed') {
  <div
    class="state-confirmed"
    role="status"
    aria-live="polite"
    tabindex="-1"
  >
    <h2 class="confirmed-heading">{{ msgs['summary.confirmed'] }}</h2>
    ...
  </div>
}
```

AC-03.14: *"la pantalla de confirmación mueve el foco a un encabezado con `role='status'` o `aria-live='polite'`"*.

El contenedor tiene `tabindex="-1"` pero el componente **no llama a `.focus()`** en el ciclo de vida. Además la plantilla no tiene una referencia `#` para localizar el elemento ni un `ViewChild`. El foco permanece donde estaba (típicamente, el botón "Pagar", si no se re-pinta).

Nota: `aria-live="polite"` por sí solo cumple el anuncio, por lo que un lector de pantalla **sí** lee el texto cuando aparece. Pero el *foco* sigue sin moverse, que es lo que el AC exige literalmente.

**Por qué importa:** el checklist §3 de la skill `review-checklist` lista accesibilidad como bloqueante. Sin foco movido, un usuario que llegó con `Enter` en "Pagar" queda con el foco en un botón que ya no existe (el botón "Pagar" desapareció al cambiar el `@switch`), lo que en algunos browsers deposita el foco en `<body>` → pérdida de contexto.

**Recomendación:**
- `@ViewChild('confirmedBox', { read: ElementRef }) confirmedBox?: ElementRef<HTMLElement>;` + `effect(() => { if (this.pageState() === 'confirmed') queueMicrotask(() => this.confirmedBox?.nativeElement.focus()); });`.
- Añadir e2e: tras click en Pagar y confirmación visible, `expect(await page.evaluate(() => document.activeElement?.tagName)).toBe('DIV')` o similar, con una comprobación de clase.
- Idéntico patrón se podría aplicar al error de pago (`role="alert"`) para consistencia.

**Estado:** open

### F-03-1.8 · minor · Cumplimiento de spec (AC-03.13, G-03.6)

**Dónde:** `apps/web/src/app/core/pricing.ts:46-57` (reutilizado por summary.component.ts:510-516)

**Evidencia:**
```ts
export function formatPrice(price: number, currency: 'COP' | 'CLP'): string {
  const locale = currency === 'COP' ? 'es-CO' : 'es-CL';
  return new Intl.NumberFormat(locale, {
    style: 'currency',
    currency,
    maximumFractionDigits: 0,
  }).format(price);
}
```

SPEC-03 AC-03.13 (ejemplos no normativos, dependen de G-03.6):
- CO: `$ 450.000 COP` (con sufijo ISO explícito)
- CL: `$ 35.000 CLP` (con sufijo ISO explícito)

G-03.6 pide *"Sufijo ISO explícito en el string final"*. `Intl.NumberFormat` con `style: 'currency'` usa el símbolo del currency pero **no añade** el código ISO como sufijo (produce `$ 450.000` para es-CO con COP, puede incluir "COP" dependiendo de la implementación del runtime). El e2e `AC-03.13 CO plan price displays COP currency format with $ symbol` asume la ambigüedad y solo verifica `$` + separador numérico (`1.200.000`), explícitamente anotando *"If the COP suffix is missing from the output, that is a spec/impl gap"*.

**Por qué importa:** los dos países comparten símbolo `$`. Sin el código ISO, un usuario viendo `$ 35.000` en móvil podría no distinguir si son COP o CLP. G-03.6 fue aprobada por el humano con `$ 450.000 COP` exacto.

**Recomendación:**
- Cambiar la formateación a `'currency', currencyDisplay: 'code'` y post-procesar para obtener `$ 450.000 COP` (un patrón común es `Intl.NumberFormat(locale, { style:'decimal', ... }).format(price) + ' ' + currency` con el símbolo manual, o usar `Intl.NumberFormat(..., { style:'currency', currencyDisplay:'symbol' })` y concatenar `' ' + currency` al final).
- Añadir test unitario a `pricing.spec.ts`: `formatPrice(450000, 'COP')` termina en `COP` y contiene `$`. Idem CLP.
- Actualizar el e2e AC-03.13 para exigir el sufijo ISO.

**Estado:** open

### F-03-1.9 · minor · Cumplimiento de spec (RN-03.1, UX)

**Dónde:** `apps/web/src/app/features/summary/summary.component.ts:120-124`

**Evidencia:**
```html
@for (entry of applicantEntries(); track entry.key) {
  <div class="data-row">
    <dt class="data-label">{{ entry.key }}</dt>
    <dd class="data-value">{{ entry.value }}</dd>
  </div>
}
```

El `<dt>` muestra la **key cruda** (`documentNumber_CO`, `fullName`, `vehicleYear`, `brand_CO`...) como etiqueta del dato. El usuario ve literalmente `documentNumber_CO: 1023456789`.

Las labels legibles ("Número de cédula", "Placa del vehículo", etc.) viven en el `FormField.label` de Strapi, pero el `WizardStore` solo persiste el `Record<string, unknown>` crudo + un `applicantFieldsSnapshot: string[]` (solo keys). No hay forma de obtener la label.

**Por qué importa:** rompe la coherencia del mensaje al usuario. La spec habla de "resumen consolidado" (SPEC-03 §1) — mostrar keys crudas no es un resumen, es un dump del estado. El e2e no lo detecta porque busca contenido (`getByText('Ana García Pérez')`) y no el label.

**Recomendación:**

### F-03-1.10 · minor · Mantenibilidad / calidad de tests (ADR-010 Validación)

**Dónde:** `apps/web/src/app/features/summary/payment.service.spec.ts:191-200` (AC-03.7)

**Evidencia:**
```ts
it('AC-03.7 two subscribers receive the same result; logStructured called once', async () => {
  // ...
  const obs1 = service.simulate('plan-abc');
  const obs2 = service.simulate('plan-abc');
  obs1.subscribe({ next: (v) => results.push(v) });
  obs2.subscribe({ next: (v) => results.push(v) });
  await vi.advanceTimersByTimeAsync(PAYMENT_SIMULATION_DELAY_MS);

});
```

El test verifica que la **misma observable** se devuelve. Pero AC-03.7 habla de *"Pulsar 'pagar' múltiples veces durante el procesamiento no dispara múltiples pagos"*. ### F-03-1.11 · minor · Mantenibilidad (Angular moderno)

**Dónde:** `apps/web/src/app/features/summary/summary.component.ts:17-24, 475-489, 555-558, 588-608`

**Evidencia:** el componente mezcla `OnInit/OnDestroy` + `Subscription.unsubscribe` manuales con signals. El patrón moderno recomendado (skill `angular-conventions`) es `takeUntilDestroyed(inject(DestroyRef))` + RxJS, o convertir las observables a signals con `toSignal`. Aquí se usa:

```ts
#termsSub?: Subscription;
#paymentSub?: Subscription;

ngOnDestroy(): void {
  this.#termsSub?.unsubscribe();
  this.#paymentSub?.unsubscribe();
}
```

**Por qué importa:** inconsistencia con el resto del proyecto (US-01 y US-02 también usan Subscriptions — la observación aplica a los tres, pero US-03 era la oportunidad de alinear). Mayor riesgo de leak si alguien añade una suscripción y olvida el `unsubscribe`. CLAUDE.md §2 pide `inject()` y signals; no habla literalmente de DestroyRef, pero la skill `angular-conventions` sí.

**Recomendación:**
- `readonly #destroyRef = inject(DestroyRef);` y en cada `subscribe(... )` añadir `pipe(takeUntilDestroyed(this.#destroyRef))`.
- Eliminar `ngOnDestroy`. Mantener `ngOnInit` para `loadTerms()` o convertirlo a `constructor` + `effect()`.
- No bloqueante; nit-major.

**Estado:** open

### F-03-1.12 · minor · Seguridad defensiva (ADR-009 §D3-A link href)

**Dónde:** `apps/web/src/app/features/summary/terms-blocks-renderer.component.ts:20-40`

**Evidencia:**
```html
@if (node().type === 'link' && safeUrl()) {
  <a [attr.href]="linkUrl()" rel="noopener noreferrer" target="_blank" ...>
```

`linkUrl()` devuelve `n.url` tal cual. `isSafeUrl` valida el esquema (http/https/mailto/relative) pero no normaliza/sanitiza el resto. Un URL válido `http://example.com/path?x=<svg onload=alert(1)>` pasa `isSafeUrl` y se interpola como `href`. Angular **sí** escapa en `[attr.href]` (equivalente a `SecurityContext.URL`), por lo que no hay XSS en el DOM, pero el browser puede interpretar la query en el servidor destino. No es XSS del cliente — es un enlace "feo" que el renderer acepta.

**Por qué importa:** ADR-009 §D3-A exige validación de enlaces como "seguridad defensiva". El check actual no cubre el caso de URLs válidas con payloads en query/fragment. En v1 el contenido lo escribe negocio en Strapi (riesgo bajo), pero la fachada de seguridad debería ser consistente.

Secundario: el test `link with javascript: url is discarded from inline children and logged` en `terms.schema.spec.ts:158-173` **no ejercita** la caída del link a texto plano en el renderer — solo verifica que el link pasa el schema (lo cual sí pasa, es `url: z.string().min(1)`). El AC-03.3 "link with javascript: url degrades to plain text" lo verifica `url-safety.spec.ts` para la función pura pero **no** hay test del renderer que confirme el degrade en el DOM.

**Recomendación:**
- Añadir test unitario / de integración del renderer: montar `TermsBlocksRendererComponent` con un paragraph+link `url: 'javascript:alert(1)'` → aserción de que el DOM resultante no tiene `<a>` y que el texto del `children` sí se interpola.
- Opcional: fortalecer `isSafeUrl` para rechazar `<`, `>`, `"`, `'` en la URL — defensa en profundidad.

**Estado:** open

### F-03-1.16 · minor · Seed / idempotencia

**Dónde:** `apps/cms/src/seed.ts:808-848` (`seedTerms`)

**Evidencia:**

El `seedTerms` busca "existing published OR draft" por `country.documentId` y salta si encuentra cualquiera. Es correcto para idempotencia. Pero:

```ts
const existingPublished = await strapi.documents('api::terms.terms').findFirst({
  filters: { country: { $eq: countryDocId } },
  status: 'published',
});
```

El filtro `country: { $eq: countryDocId }` asume que la API del Document Service acepta ese shape para relaciones. En Strapi 5, el filtro canónico es `country: { documentId: { $eq: ... } }` o `country: { $eq: countryDocId }` (dependiendo de versión). El seed de `seedPlans` usa la misma estructura (`country: { $eq: ... }`), por lo que si uno funciona el otro también. Pero no hay test de integración que lo pruebe en el CI; depende de `docker compose up` manual.

**Por qué importa:** si el filtro no tiene el shape correcto, `findFirst` devuelve `null` siempre → el seed crea un `terms` nuevo en cada arranque. Degrada la idempotencia sin romper nada visible.

**Recomendación:**
- Añadir un test de arranque (una vez que exista infra de test CMS): tras dos `bootstrap` consecutivos, hay exactamente un `terms` por país.
- O un e2e que `GET /api/legal-terms?filters[country][code][$eq]=CO&pagination[limit]=100` tras dos arranques y afirmar `data.length === 1`.

**Estado:** open
