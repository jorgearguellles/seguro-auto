# REV-02-2 — Lista de planes por país con selección persistente (US-02, re-review)

## Resumen

critical: 0 · major: 1 · minor: 4 · nit: 2

Los **cinco hallazgos bloqueantes** de REV-02-1 (F-02-1.1 .. F-02-1.5) quedan **resueltos** con evidencia reproducible. En particular:

- El re-etiquetado del `paso-2.spec.ts` (commit `66072ec`) deja cada `test.describe` / `test` apuntando al AC que verifica. Los dos ACs huérfanos recuperaron cobertura: **AC-02.7** con un round-trip paso-2 → paso-3 → paso-2 por SPA navigation preservando la selección (líneas 473-507), y **AC-02.9** con una navegación directa a `/co/paso-2` sin `WizardStore.applicant()` que redirige a `/co/paso-1` (líneas 535-545). Se añadió además `wizard-step.guard.spec.ts` con dos casos unitarios que cubren el camino "applicant → true" y el camino "null → UrlTree a paso-1".
- El patrón radiogroup real está implementado: `tabindex` gobernado por `getFocusedTabIndex(i)` (solo el `focusedPlanIndex` tiene `tabindex="0"`), handlers de `ArrowRight`/`ArrowDown`/`ArrowLeft`/`ArrowUp` que mueven foco + selección con wraparound (`moveFocus`), y `Home`/`End` que saltan a extremos (`moveFocusTo`). Los `setTimeout` para enfocar después del render son un recurso aceptable con `QueryList`. El e2e correspondiente (paso-2.spec.ts:768-799) ya presiona `ArrowRight`, `ArrowDown` y `ArrowLeft` reales, no `Tab`.
- `aria-labelledby` reemplaza al `aria-label="plan.name"`: apunta a `plan-name-{documentId}` + `plan-badge-{documentId}` (solo si `recommended`) + `plan-price-{documentId}`. El badge perdió su `aria-label` redundante y queda como texto visible asociado al nombre accesible del radio.
- `angular.json` confirma `inlineStyleLanguage: "scss"` (línea 27).

Queda **un hallazgo nuevo**: el fix F-02-1.3 eliminó `aria-label="Recomendado"` del badge pero el test `AC-02.4 recommended badge is accessible to screen readers` (paso-2.spec.ts:383-391) sigue buscando `page.locator('[aria-label="Recomendado"]')`. El selector ya no coincide con nada en el DOM y el test fallará en runtime — es el mismo patrón "test que miente por diseño" que la propia F-02-1.1 denunció, solo que ahora en sentido inverso (el código correcto, el test desactualizado). Lo marco `major` porque bloquea la suite de e2e si se ejecuta, oculta cobertura real de AC-02.4 y contradice la cadena US → SPEC → AC → test.

Los hallazgos menores de REV-02-1 (F-02-1.6 a F-02-1.11, F-02-1.12) **siguen abiertos**. No eran bloqueantes para QA y el humano no los marcó como prioritarios; los mantengo listados con estado `open` para que queden en el historial.

Como en REV-01-1 y REV-02-1, **no pude ejecutar `npm --prefix apps/web test` ni `lint` en este sandbox**: las ejecuciones de Bash están bloqueadas por política. La revisión se apoya en lectura estática, `grep` y la lectura del diff aplicado por los commits `4d9d17e` y `66072ec`.

Ambas son conformes. La variante (a) es la más común y la que probaron los tests. Dejar así.

## Nuevos hallazgos

### F-02-2.1 · major · Calidad de tests (AC-02.4)

**Dónde:** `apps/web/e2e/paso-2.spec.ts:383-391`.

**Evidencia:**

```ts
test('AC-02.4 recommended badge is accessible to screen readers', async ({ page }) => {
  await mockFieldsAndPlans(page, CO_PLANS_RESPONSE);
  await completePaso1(page);

  // The badge element has aria-label="Recomendado" (or the text itself is readable)
  // The component uses <span class="badge" aria-label="{{ msgs['plans.recommended'] }}">
  const badge = page.locator('[aria-label="Recomendado"]').first();
  await expect(badge).toBeVisible();
});
```

El fix F-02-1.3 (`4d9d17e`) eliminó el `aria-label="Recomendado"` del badge (plans.component.ts:118-124 ahora sólo renderiza `<span [id]="'plan-badge-...'" class="badge badge--recommended">Recomendado</span>`). `grep -rn "aria-label" plans.component.ts` confirma que la única ocurrencia de `aria-label` en el componente es ya `aria-labelledby`. El selector `[aria-label="Recomendado"]` no coincidirá con nada en el DOM renderizado y `expect(badge).toBeVisible()` fallará con "locator resolved to 0 elements".

Además, el comentario interno del propio test (líneas 387-388) todavía documenta la implementación anterior (`<span class="badge" aria-label="{{ msgs['plans.recommended'] }}">`), lo que confunde a cualquier mantenedor que lo lea.

**Por qué importa:**

- El test fallará en CI al ejecutarse — rompe la suite e2e de US-02.
- Es exactamente el patrón "test que miente por diseño" que REV-02-1 F-02-1.1 denunció, aquí en sentido inverso: ahora el código accesible correcto y el test desactualizado. La cadena `US → SPEC → AC → test` para AC-02.4 queda rota hasta corregir.
- AC-02.4 pierde su segunda capa de cobertura de accesibilidad. Los otros dos tests del describe (`AC-02.4 plan with recommended=true shows "Recomendado" badge` y `AC-02.4 plans with recommended=false do NOT show the badge`) usan `getByText('Recomendado')` y siguen válidos, pero no prueban "perceptible por lector de pantalla".
- No lo clasifico `critical` porque la cobertura visual del badge sigue en pie por los dos tests que sí usan `getByText`; sí lo clasifico `major` porque bloquea la suite e2e y requiere acción antes de QA.

**Recomendación:**

Reescribir el test para verificar el nombre accesible del radio-group item, que ahora incluye el texto del badge por `aria-labelledby`:

```ts
test('AC-02.4 recommended badge is included in the plan radio accessible name', async ({ page }) => {
  await mockFieldsAndPlans(page, CO_PLANS_RESPONSE);
  await completePaso1(page);

  // "Estándar" es recommended:true en el fixture.
  // El nombre accesible del role=radio incluye el badge por aria-labelledby.
  const estandarRadio = page.getByRole('radio', { name: /Estándar.*Recomendado/ });
  await expect(estandarRadio).toBeVisible();
});
```

Alternativa complementaria: una aserción sobre `getAttribute('aria-labelledby')` que confirme que la lista de ids incluye `plan-badge-{documentId}` cuando `recommended=true`. Y actualizar el comentario de las líneas 387-388 a la implementación actual.
