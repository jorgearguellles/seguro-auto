# REV-01-1 — Formulario configurable del paso 1 (US-01)

## Resumen

critical: 2 · major: 4 · minor: 5 · nit: 3

El front-end está bien estructurado (standalone, signals, OnPush, zod, reactive forms tipados). La historia de seguridad al nivel del front se cumple: no hay tokens, no hay `populate=*`, no hay `innerHTML`, no hay `localStorage`/`sessionStorage`. La trazabilidad por AC en títulos de test es consistente.

Sin embargo, hay **dos bugs críticos de integración** entre el CMS y el front:

1. El enum de reglas de validación en Strapi (`cedulaCO`, `plateCO`, `rutCL`, etc., camelCase) **no coincide** con el enum de zod/registro del front (`cedula_co`, `placa_co`, `rut`, etc., snake_case). Consecuencia: al correr contra Strapi real, **todas** las reglas custom se descartan silenciosamente como `unknownRule`. La app pierde RN-01.12 por completo y AC-01.6/AC-01.7 solo pasan en e2e porque los mocks usan el nombre snake_case.
2. El botón "Continuar" no se deshabilita cuando el formulario es inválido, contradiciendo AC-01.2 ("el botón que avanza al paso 2 permanece deshabilitado") y AC-01.3. El propio handoff del builder (nota en `e2e/paso-1.spec.ts:198`) reconoce que el test falla contra la implementación actual.

Hay además violaciones a ADRs (enum literal diferente al pactado en ADR-001/ADR-006, `email` añadido al enum de Strapi sin justificación en ADR) y el `country` content-type expone `termsAndConditions: blocks` siendo `country.find` accesible al rol Public (fuera de alcance de SPEC-01, pero conviene dejarlo registrado antes de US-03).

No pude ejecutar `npm --prefix apps/web test` ni `lint` dentro del sandbox (comandos bloqueados). La revisión se apoya en lectura estática del código. Los hallazgos se verificaron con `grep` y lectura manual.

## Hallazgos

### F-01-1.1 · critical · Cumplimiento de spec / ADR (RN-01.12, ADR-001, ADR-006)

**Dónde:**
- `apps/cms/src/components/field/validation.json:11-26` (enum Strapi en camelCase + `email` extra)
- `apps/cms/src/seed.ts:30-36, 133, 150, 168, 184, 248, 265, 283, 299` (seed usa camelCase)
- `apps/web/src/app/core/schemas/form-field.schema.ts:11-24` (enum zod en snake_case)
- `apps/web/src/app/features/applicant-form/validator-registry.ts:20-33` (registro en snake_case)

**Evidencia:** El CMS publica reglas con nombres `cedulaCO`, `plateCO`, `plateCL`, `rutCL`, `minAge`, `vehicleYear` (más un `email` no documentado). El front sólo acepta `cedula_co`, `placa_co`, `patente_cl`, `rut`, `mayor_edad`, `anio_vehiculo`. `sanitizeValidations` en `form-field.schema.ts:66-74` descarta cualquier regla fuera de ese enum vía `logStructured('strapi.formFields.validationDiscarded', {reason: 'unknownRule'})`.

Resultado contra un Strapi real: cada campo pierde todas sus reglas custom antes de llegar al form-builder → RUT, cédula, placas, mayoría de edad y rango de año nunca se ejecutan. Solo `Validators.required` sobrevive (porque se añade por bandera `required`, no por la regla). Esto rompe RN-01.12, AC-01.6, AC-01.7 y vacía la lógica que motivó ADR-004.

**Por qué importa:** Es una **silent failure de seguridad y UX**: el usuario puede enviar un RUT `0-0` o una placa `AAA` y avanzar. Los e2e pasan porque los fixtures (`e2e/fixtures/form-fields.ts:33, 46, 59, 109, 122`) usan los nombres snake_case del front, no los del CMS real → cobertura falsa.

ADR-001 §Esquema fija literalmente el enum `rule` como `required, min, max, minLength, maxLength, pattern, rut, cedula_co, placa_co, patente_cl, mayor_edad, anio_vehiculo`. ADR-006 fija el mismo enum en zod. El builder se desvió sin ADR superseding.

**Recomendación:** Elegir **una** nomenclatura y alinear los tres sitios + fixtures:
- Preferido: respetar ADR-001/ADR-006 (snake_case) → cambiar `validation.json`, `seed.ts` y los `ValidationRule` type aliases del CMS.
- O bien: abrir un ADR-007 que supersede la parte relevante de ADR-001/ADR-006, migrar el enum zod a camelCase y justificar `email` o removerlo.
- Añadir un test de contrato que compare el enum de `validation.json` con el enum de zod en tiempo de build (parsear el JSON y afirmar igualdad), para que este drift sea imposible en el futuro.

**Estado:** open

### F-01-1.2 · critical · Cumplimiento de spec (AC-01.2, AC-01.3)

**Dónde:** `apps/web/src/app/features/applicant-form/applicant-form.component.ts:87-95`

**Evidencia:**
```
<button
  type="submit"
  class="btn btn--primary"
  [disabled]="isSubmitting()"
  [attr.aria-busy]="isSubmitting() ? 'true' : null"
>
  Continuar
</button>
```

El botón solo se deshabilita mientras `isSubmitting()` es `true`. En estado inicial (formulario vacío, inválido) o con errores pendientes, `isSubmitting()` es `false` y el botón queda habilitado. El propio e2e lo documenta (`e2e/paso-1.spec.ts:197-201`):
```
// NOTE: this test FAILS on the current implementation — see BUG-01 in handoff.
// The implementation only disables the button during isSubmitting(), not on invalid state.
const submitBtn = page.getByRole('button', { name: 'Continuar' });
await expect(submitBtn).toBeDisabled();
```

**Por qué importa:** AC-01.2 exige explícitamente "el botón que avanza al paso 2 permanece deshabilitado" cuando hay un campo inválido; AC-01.3 lo repite ("permanezco en el paso 1 ... y cada campo obligatorio inválido muestra su mensaje"). Aunque `onSubmit` sí previene la navegación cuando el form es inválido, dejar el botón habilitado es un fallo de UX y de contrato de la spec. También lo afirma AC-01.11 ("el botón para avanzar al paso 2 permanece deshabilitado") en estado vacío — ahí la plantilla ni siquiera renderiza el botón, lo cual está bien para ese estado.

**Recomendación:**
- Convertir el estado inválido en un signal derivado (`invalid = toSignal(form.statusChanges, { initialValue: form.status === 'INVALID' })` o similar) y combinarlo con `isSubmitting()`:
  `[disabled]="isSubmitting() || formInvalid()"`.
- Mantener igualmente la validación en `onSubmit` como defensa (hoy ya la hace).
- Verificar que el test e2e de AC-01.2 (que hoy es espec + bug reconocido) pase sin ajustar.

**Estado:** open

### F-01-1.3 · major · Cumplimiento de spec (AC-01.11)

**Dónde:** `apps/web/src/app/features/applicant-form/applicant-form.component.ts:66-70`

**Evidencia:** En estado `empty`, la plantilla no renderiza el botón "Continuar" (correcto), pero la copia es el `role="status"` genérico (`<div role="status" class="state-empty">`) junto a la otra región de carga. Dos elementos con `role="status"` en el DOM, con mensajes distintos ("Cargando" y "No hay campos"), confunden a lectores de pantalla porque cada uno es una live region independiente, pero el cambio del `@switch` sustituye el nodo sin anunciar la transición.

**Por qué importa:** AC-01.11 pide un estado vacío accesible. El contenedor `role="status"` es correcto, pero al compartir el mismo `role` con el estado de carga sin un único live-region estable, los cambios de estado pueden perderse o anunciarse como duplicados. Es una fricción de accesibilidad real que `axe` no caza (`axe` solo valida la presencia de atributos, no la coreografía de live regions).

**Recomendación:**
- Usar un único live region raíz (`<div aria-live="polite" aria-atomic="true">`) dentro del cual se renderiza el mensaje del estado activo. Reservar `role="status"` solo para el estado de carga; usar un párrafo normal para el estado vacío.
- O etiquetar el estado vacío con `role="region"` + `aria-label` y dejar `role="status"` solo en loading.

**Estado:** open

### F-01-1.4 · major · Cumplimiento de spec / ADR (AC-01.3, ADR-004 §Diseño concreto)

**Dónde:** `apps/web/src/app/features/applicant-form/applicant-form.component.ts:267-277`

**Evidencia:**
```
onSubmit(): void {
  if (this.isSubmitting()) return;
  const f = this.form();
  f.markAllAsTouched();
  f.updateValueAndValidity();
  if (f.invalid) { this.#focusFirstInvalidField(); return; }
  ...
}
```

`markAllAsTouched` solo marca los controles como `touched`; con `updateOn: 'blur'` esto **no dispara** la re-ejecución de los validadores si el usuario nunca llegó a enfocar y desenfocar el campo. `updateValueAndValidity()` sí lo hace, pero su comportamiento en un `FormGroup` con hijos `updateOn: 'blur'` es inconsistente: en Angular ejecuta los validadores del grupo pero no fuerza re-evaluación profunda de los hijos. El e2e `AC-01.3 clicking Continuar with empty form` depende de que los mensajes de los controles obligatorios aparezcan tras el submit; con `updateOn: 'blur'` sin blur previo, los `control.errors` se pueden computar pero el renderer (`field-renderer.component.ts:245-266`) solo muestra el error cuando `ctrl.touched || ctrl.dirty`. `markAllAsTouched` ayuda, pero la secuencia es frágil y depende de que `statusChanges` se dispare.

**Por qué importa:** ADR-004 §Foco al primer error exige `form.markAllAsTouched()` + `form.updateValueAndValidity()` + recorrer en orden. El código lo hace, pero no garantiza que los `errorMessage` se rendericen en el primer submit cuando el usuario nunca tocó los campos (caso del e2e AC-01.3). Riesgo de test flaky o regresión.

**Recomendación:**
- Tras `markAllAsTouched`, iterar los controles del grupo (`Object.values(form.controls)`) llamando a `ctrl.updateValueAndValidity({ emitEvent: true })` individualmente. Eso garantiza recomputación y disparo de `statusChanges` para cada field-renderer.
- Añadir un test unitario en `applicant-form.component.spec.ts` (no existe) que monte el componente con fixture, haga click en Continuar sin tocar campos, y afirme que todos los mensajes de error están visibles.

**Estado:** open

### F-01-1.5 · major · Seguridad / preparación de US-03 (ADR-003 §D5)

**Dónde:** `apps/cms/src/api/country/content-types/country/schema.json:34-36`

**Evidencia:**
```
"termsAndConditions": {
  "type": "blocks"
}
```

El content-type `country` tiene un campo `blocks` (rich text) y `PUBLIC_READ_V1` incluye `api::country.country.find` (bootstrap/index.ts:24-28). ADR-003 §D5 afirma textualmente: "ningún atributo de `form-field` consumido por el rol Public puede ser `blocks` sin un nuevo ADR" — y aunque el texto habla de `form-field`, el principio (prevenir XSS en v1) aplica a cualquier atributo expuesto al rol Public. SPEC-01 no consume `country.termsAndConditions`, pero el campo está listo para que US-03 lo pinte, y nadie ha escrito el ADR del renderer de bloques seguro.

En SPEC-01 el front sólo usa `country` indirectamente vía `filters[country][code][$eq]=…` sin `populate`, por lo que **hoy** no hay vector XSS activo. Lo registro como `major` porque entra en la superficie de datos públicos, y el checklist §1 "sin `innerHTML` sin sanitizar" obliga a dejar documentada la expectativa antes de que US-03 llegue y alguien pinte el campo con `[innerHTML]` por descuido.

**Por qué importa:** La regla de CLAUDE.md §7 es "texto enriquecido de Strapi se renderiza sin `innerHTML` sin sanitizar". Dejar el campo expuesto sin ADR invita a que US-03 lo consuma rápido y pegue el HTML crudo.

**Recomendación:**
- Decisión A: mover `termsAndConditions` al scope de US-03 (eliminar del schema actual, agregar en el ADR de US-03 junto al renderer de bloques).
- Decisión B: dejar el campo (para no migrar datos) pero añadir una nota en el bootstrap (`PUBLIC_READ_V1`) advirtiendo que un cliente puede ya leer `termsAndConditions`, y tomar el compromiso explícito de implementar renderer de bloques antes de pintarlo.
- No depende de este review, pero debería bloquearse en HITL-3.

**Estado:** open

### F-01-1.6 · major · Cumplimiento de spec (AC-01.14)

**Dónde:** `apps/web/src/app/features/applicant-form/applicant-form.component.ts:101-201`, `apps/web/src/app/features/applicant-form/field-renderer.component.ts:126-190`

**Evidencia:** El componente lleva estilos inline (con sintaxis SCSS: `&:disabled`, anidamiento, `@media`), pero Angular `styles` en metadata **no procesa SCSS** por defecto (requiere compilador SCSS en los `styles` del componente, no sólo en `styleUrls`). El `angular.json` configura SCSS para `styles` globales pero no para inline `styles:` array; en Angular 21 los styles inline se tratan como CSS literal y Angular avisa en build si hay SCSS inline. Si el build funciona (depende del esbuild/application builder), puede estar permitiéndolo gracias a `inlineStyleLanguage`. No veo esa opción en `angular.json:architect.build.options`.

**Por qué importa:** AC-01.14 pide que el formulario sea usable en 375 y 1280 px. Si el SCSS inline no se compila, los media queries y el `min-height` fallan, y los e2e `AC-01.14` fallarían contra un `ng build` real (no contra `vitest`, que carga los `.ts` y no procesa estilos).

**Recomendación:**
- Añadir en `angular.json:architect.build.options` la propiedad `"inlineStyleLanguage": "scss"`.
- O migrar los estilos a `styleUrl:` con archivos `.scss` dedicados.
- Añadir un smoke test `ng build` en CI/handoff para detectar esto.

**Estado:** open

### F-01-1.11 · minor · Mantenibilidad / mantenimiento del tipo

**Dónde:** `apps/web/src/app/features/applicant-form/validator-registry.ts:22-26`

**Evidencia:** El registro usa `as { value: number }` y `as { regex: string }` sin propagar el tipo refinado del `paramsByRule` del schema (ADR-006 §Diseño concreto). zod ya parsea los params (`sanitizeValidations`), pero el registro vuelve a confiar en un `as` ciego.

### F-01-1.15 · nit · Convenciones / limpieza

**Dónde:** `apps/web/src/app/features/applicant-form/field-renderer.component.ts:220-226`

**Evidencia:**
```
get control(): FormControl {
  const ctrl = this.formGroup().get(this.field().key);
  if (!ctrl) {
    throw new Error(`[FieldRenderer] No control found for key: ${this.field().key}`);
  }
  return ctrl as FormControl;
}
```

Un `get control()` llamado varias veces por `ngOnInit`, `#watchStatus`, `#updateErrorState` y `#resolveErrorMessage` hace `formGroup().get(...)` cada vez, lo que invalida la posibilidad de memoización. El throw es correcto, pero el patrón `get` mezcla efectos secundarios (fallo) con lectura idempotente.

**Por qué importa:** Es más un estilo que un bug. El `as FormControl` evita tipado estricto; si el campo es de tipo `number`, Angular devuelve igualmente un `FormControl<unknown>`.

**Recomendación:** Reemplazar el getter por un `computed<FormControl>` memoizado en `formGroup()` + `field()` y hacer el throw en `ngOnInit`. Mínimo: mantener el getter pero evitar el cast `as FormControl`.
